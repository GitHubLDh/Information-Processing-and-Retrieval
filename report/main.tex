\begin{abstract}
Existing movie search tools let users filter by title, genre, cast, or year, but fail
when a user remembers only a vague plot detail rather than exact metadata. We combine
structured movie metadata and user reviews from \textit{The Movie Database (TMDB)
Comprehensive Dataset} with plot text from English Wikipedia, linking records by TMDB
ID through Wikidata rather than matching titles and years. The resulting collection of
6{,}104 movies carries long, narrative plot text (511 words on average) alongside
12{,}057 reviews, together contributing nearly 99{,}000 unique word forms --- far
exceeding the length of TMDB's own overview field. This combination of structured
fields, narrative plot summaries, and reviewer opinion produces a collection suited to
retrieval by remembered plot details, themes, and reception, rather than by exact
metadata alone.
\end{abstract}

\keywords{information retrieval, movie dataset, data collection, Wikipedia, Wikidata, text characterization}

\section{Topic}
Movies are a common dataset choice, so the retrieval goal deliberately does not center
on metadata search (genre, year, cast) that any catalog already supports well. Instead,
the goal is retrieval driven by \emph{what a user remembers about a movie} --- a plot
detail, a theme or a narrative trope --- rather than what they can already filter for. 
This motivates linking structured TMDB metadata with two
free-text sources: Wikipedia plot summaries (narrative content) and TMDB user reviews
(reception and opinion), so that information needs can be phrased the way people
actually half-remember movies, not the way a database schema represents them. For
example: \textit{``A story where the main character can't trust their own memories or
perception of reality, and slowly uncovers a hidden truth about who they really
are.''} No metadata field captures this, and no single keyword match is reliable
either --- it requires matching the collection's free text to a vaguely-recalled theme.

\section{Data Sources}

\subsection{The Movie Database (TMDB) Comprehensive Dataset}
Kaggle dataset by rishabhkumar2003~\cite{tmdb-kaggle}, sourced from the TMDB API. Five CSV files:
\texttt{movies.csv} (9{,}771 rows --- one per movie; title, overview, release date,
runtime, budget, revenue, rating, vote count, genres, language), \texttt{cast.csv}
(\textasciitilde150{,}000 rows), \texttt{crew.csv} (\textasciitilde63{,}600 rows),
\texttt{genres.csv} (a 20-row reference table, not a per-movie join table --- genres are
already embedded in \texttt{movies.csv}), and \texttt{reviews.csv} (user reviews,
13{,}073 rows after parsing). No IMDb ID field exists in this dataset. The dataset is
licensed CC~BY-NC-SA~4.0 --- non-commercial use with attribution and share-alike, which
is compatible with this (non-commercial, academic) project.

\paragraph{Authority assessment.} The dataset is published by a third-party Kaggle
contributor (rishabhkumar2003), not by TMDB itself, but its acquisition method is
documented (the official TMDB API) and the underlying source, TMDB, is a
long-established, actively moderated community movie database used by numerous
production applications (e.g.\ Plex, Kodi), which lends indirect authority. Per-row
\texttt{created\_at}/\texttt{updated\_at} timestamps indicate a recent snapshot
(February 2026). During cleaning we spot-checked several well-known entries (e.g.\
\textit{Interstellar}, \textit{Star Wars}) and found their metadata plausible and
accurate.

\subsection{Wikipedia}
Plot summaries are retrieved from English Wikipedia through the MediaWiki API's
\texttt{action=parse} endpoint~\cite{wikipedia,mediawiki-api}, which returns the
rendered HTML of an article as JSON. Each article is linked to a TMDB movie through
Wikidata~\cite{wikidata}, using the TMDB movie ID property (P4947), instead of by
title. An early attempt that looked articles up by plain title returned
disambiguation pages for some films (e.g.\ \textit{Interstellar}), so title matching
was not reliable. Only the Plot section of each article is kept. Wikipedia text is
available under the CC~BY-SA~4.0 license~\cite{wikimedia-terms}, which requires
attribution and share-alike and is compatible with this non-commercial academic
project. Requests are limited to one per second, following the API usage guidelines.
 
\paragraph{Authority assessment.} Wikipedia's authority is crowd-sourced rather than
centrally verified: article quality depends on how actively a page is edited and
cited. High-profile films tend to have well-maintained, citation-backed articles,
while niche titles may have thin or stale ones --- a disparity already visible in our
linking results, where mainstream genres (e.g.\ Adventure, Action) link to an English
Wikipedia article far more often than niche categories (e.g.\ Documentary, TV Movie).
For this project the relevant content is the plot summary, which follows a common
editorial convention (present tense, spoilers included) and is therefore fairly
uniform across articles, although its completeness still depends on how well a page
is maintained.

\section{Collection \& Preparation}
The collection pipeline has four stages, run by different group members and merged
into a single final collection (Figure~\ref{fig:dfd}):
\begin{enumerate}
  \item \textbf{Movies/reviews cleaning} --- deduplicate movies, drop movies with no
    release date, clean review text (strip HTML/Markdown formatting), drop empty or
    very short (\textless20 words) reviews, drop duplicate reviews. Result:
    9{,}771 $\rightarrow$ 9{,}710 movies, 13{,}073 $\rightarrow$ 12{,}248 reviews.
  \item \textbf{Wikidata linking} --- resolve each TMDB ID to an English Wikipedia
    article title via Wikidata property P4947. 7{,}016 / 9{,}710 movies (72.3\%)
    linked successfully. Of the 2{,}694 unmatched IDs, 1{,}614 had no Wikidata item
    returned for the supplied TMDB ID, while 1{,}080 matched an item without an
    English Wikipedia sitelink. The first count does not establish that no Wikidata
    item exists; an item may lack the TMDB identifier. This Kaggle dataset has no
    IMDb ID column, so an IMDb fallback was unavailable.
  \item \textbf{Wikipedia fetching \& parsing} - each linked article is requested
    through the MediaWiki API (redirects followed, one request per second, up to
    three retries on failure) and the raw JSON response is cached unchanged, one
    file per movie, so that parsing can be rerun without downloading anything
    again. A separate script then extracts the Plot section from the cached HTML and every movie 
    receives a status: plot extracted, \texttt{no\_plot} (the article was fetched but no
    matching section was found), or not fetched. In the final run, 7{,}014 of the
    7{,}016 linked titles were fetched (2 could not be fetched), and 6{,}478 plots
    were extracted (92.3\% of the linked titles). The 536 \texttt{no\_plot}
    articles are pages where the parser found no matching Plot section, not failed
    downloads.
    \item \textbf{Final join} --- aggregate cast and crew to one row per movie, then
    merge cleaned movies, reviews, cast/crew, Wikidata links, and Wikipedia plots into
    one JSONL document per movie, validating every document against our JSON Schema.
    A movie is kept only if its article yielded a plot of at least 50 words: the join
    writes \textbf{6{,}104} documents from the 9{,}709 movies (3{,}231 have no usable
    plot, 374 a plot under 50 words), carrying 12{,}057 reviews. 
\end{enumerate}

\section{Characterization}

\subsection{Wikipedia plots}
Of the 7{,}016 linked movies, 6{,}478 (92.3\%) have an extracted plot. Across all 9{,}710 cleaned movies this is 66.7\%,
so plot-based retrieval can only reach movies that have an English Wikipedia article
with a recognizable plot section.

  \label{tab:plot-coverage}

    Fetched but no plot section      &     536 &  7.6 \\

    \bottomrule
  \end{tabular}

Plots average 511 words (median 580, range 10 to 3{,}253), about twice the length of
an average review (239 words). They are narrative rather than evaluative: they retell
events and characters, while reviews express opinions. They are also much longer than
TMDB's own overview field, which is the main reason
for adding Wikipedia: it supplies the long free text that the Kaggle data lacks.
These plots are the field that the plot-based information
needs will be matched against in Milestone 2, where their usefulness for retrieval
will be measured.

\subsection{Reviews}
Of 9{,}710 cleaned movies, 6{,}013 (62\%) have zero reviews after cleaning; review
coverage is sparse and concentrated on popular titles. Movies with at least one review
average 1.26 reviews (median 0 across all movies, since most have none); reviews
average 239 words (median 181), with a right-skewed distribution
(Figure~\ref{fig:review-length-hist}). Review length shows essentially no correlation
with a movie's rating (Pearson $r = 0.115$, $n=3{,}697$), visible as a dense, largely
flat scatter in Figure~\ref{fig:review-length-rating}. The most frequent words across
all reviews, after stopword removal, are dominated by generic film-review vocabulary
(\textit{story, character, cast, plot, scenes}) rather than genre-distinctive terms.

\subsection{Wikidata linking}
Wikidata-linking coverage varied by release period and genre. It was 78.5\% for
2000s films and 66.7\% for 2020s films (not a monotonic trend by age); by genre it
was 90.9\% for Adventure and 92.1\% for Western, compared with 37.4\% for
Documentary and 41.3\% for TV Movie. Genre counts overlap. In a manual check, eight
successful sample links were confirmed against their movie pages. A 20-title
unmatched-title spot check found collisions such as \emph{Rita} and \emph{Roxanna}
(disambiguation pages) and \emph{The Photographer} (redirecting to a disambiguation
page), supporting identifier-based rather than title-only linking. Figures
\ref{fig:wikidata-decade} and~\ref{fig:wikidata-genre} show the coverage differences.

\subsection{Joined collection}
The final collection holds 6{,}104 documents. Every document has a title, plot,
\texttt{wikipedia} object, and vote count; coverage is 99\% for cast, crew, director,
and runtime, but only 61\% for budget and 63\% for revenue (TMDB stores these as 0,
which the schema maps to \texttt{null}). Genre and era coverage follow the source
data: Drama (2{,}670), Comedy (1{,}937), and Thriller (1{,}608) lead, and 4{,}290 of
the 6{,}104 films (70\%) are from the 2000s--2020s. The plot field dominates the free
text (median 596 words against a 240-character median overview), which is why it is
the main retrieval signal; plots and reviews together contribute nearly 99{,}000
unique word forms (case-folded). Missing-value hygiene holds throughout: no
empty-string or zero placeholders survive the join, and every nullable field is
\texttt{null}.

\section{Prospective Search Tasks}
Information needs are deliberately phrased around themes, situations, and reception
rather than metadata filters, since the latter is already well-served by existing
movie catalogs.

\begin{enumerate}
  \item A movie whose reviewers describe the comedy as clever, witty, or
    intellectually sharp, rather than slapstick or lowbrow.
  \item A cliché romantic movie that people call predictable or genuinely heartwarming.
  \item A science-fiction survival film about astronauts stranded away from Earth who
    need to survive or get home.
  \item A crime or thriller film in which an FBI agent investigates serial killings.
  \item A film starring Robert De Niro about italian-American maffia.
\end{enumerate}

\section{Solr Query Configuration: Setup A}

Setup A is the baseline: plain field queries with the default Lucene parser, no
field weighting, no phrase proximity, and no minimum-match tuning. Review-based
needs (Q1, Q2) query the nested \texttt{review} children through Solr's block-join
parent parser with \texttt{score=max}, exactly as in Setup B, so that query
sophistication is the only variable between the two setups rather than the
underlying document model. Plot-based needs (Q3--Q5) search the \texttt{plot} field
directly. The output contract matches Setup B: one row per movie, numeric
\texttt{movie\_id} as the run and qrels identifier, Solr's \texttt{id=movie-<movie\_id>}
retained for traceability.

For Q1 and Q2, the block-join query searches \texttt{review\_text} for a small,
hand-picked set of terms (e.g.\ \textit{clever}, \textit{witty},
\textit{intellectually sharp} for Q1) with plain \texttt{OR} matching; a hard genre
filter restricts Q1 to comedies and Q2 to romance movies. For Q3, an early version
matched \textit{astronaut} and \textit{stranded}/\textit{survive} as independent
\texttt{OR} terms, which over-matched: the plot field alone returned more than
1{,}000 candidates on either word in isolation, so the adopted query requires
\textit{astronaut} \texttt{AND} at least one of \textit{stranded}/\textit{survive}
together in the same document. Q4 similarly requires \textit{FBI} \texttt{AND}
\textit{"serial killer"} jointly, since either concept alone matches many unrelated
crime films. Q5 combines a hard cast-name filter for Robert De Niro with a plain
\texttt{OR} search over mafia vocabulary in the plot field, with an explicit
exclusion for \textit{"Russian mafia"}: an earlier version without this exclusion
returned \textit{Ronin}, confirmed by manual review to be about Russian, not
Italian-American, organized crime.

Setup A returns 162, 91, 14, 7, and 8 documents for Q1--Q5, respectively ---
smaller candidate pools than Setup B's broader, weighted matching, consistent with
Setup A's role as the precision-oriented baseline. Full per-query results and
parameters are saved in \texttt{runs/A\_Q1.json} through \texttt{runs/A\_Q5.json},
and the configuration table and A/B comparison are presented in the following
section.

\section{Solr Query Configuration: Setup B}

Setup B uses eDisMax to weight fields and close phrase matches according to each
information need. Review-based needs query the nested \texttt{review} children and
use Solr's block-join parent parser with \texttt{score=max}; the returned documents
are parent movies ranked by their best matching review. Plot-based needs search the
parent movie fields directly. The output contract is one row per movie, with the
numeric TMDB \texttt{movie\_id} as the run and qrels identifier and Solr's
\texttt{id=movie-<movie\_id>} retained for traceability.

For Q1 and Q2, eDisMax searches \texttt{review\_text}; phrase boosts reward nearby
reviewer descriptors. The parent genre filter restricts Q1 to comedies and Q2 to
romance movies. For Q3, the overview receives the strongest boost because it states
the central plot, while the longer plot field provides supporting evidence; a
science-fiction genre boost raises likely matches without imposing a hard genre
filter. For Q4, a serial-killing concept is required while FBI/investigator terms
are optional; crime/thriller genres receive a secondary boost. A local Solr check
returned 86 matches with \texttt{mm=1} and 109 with \texttt{mm=0}, confirming that
the minimum-match setting affects recall; the top 20 were identical. Setup B now
uses \texttt{mm=0} so these terms can add evidence without being required. For Q5,
a cast filter requires a Robert De Niro spelling variant, while
the eDisMax query searches overview and plot for Mafia-related wording. The cast
filter does not boost scores because every returned movie satisfies it; phrase
boosting applies to the overview field.

The previously saved Setup B runs returned 216, 205, 70, 11, and 14 documents for
Q1--Q5, respectively. These counts and rankings predate the current query-file
revision and are retrieval totals, not relevance counts; rerun Setup B before
using them to pool or judge the current queries. Manual inspection of that earlier
run found several false positives among the broadened Q3--Q5 candidates. Full per-query results and parameters are saved in
\texttt{runs/B\_Q1.json} through \texttt{runs/B\_Q5.json}.
